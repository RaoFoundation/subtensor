---
title: Wallet crypto types
description: Create, recover, sign, and transact with Ed25519, Sr25519, hashed, and ML-DSA wallets.
---

Choose a scheme when creating or recovering a wallet:

```bash
btcli wallet create --crypto-type mldsa
btcli wallet regen-coldkey --crypto-type mldsa
```

`--type` remains an alias for `--crypto-type`. The choice applies to both coldkey
and hotkey unless `--hotkey-crypto-type` overrides it. Existing keyfiles retain
their scheme; ordinary commands read that scheme automatically.

These APIs require `bittensor-core>=0.1.7`; publish the native package and the
matching Python SDK together.

ML-DSA accounts require ML-DSA proxy delegates and, when used as hotkeys,
ML-DSA coldkey owners. Registration rejects a weaker existing owner, and a
coldkey swap cannot downgrade that protection. ML-DSA authorities can still
control classical hashed accounts, allowing upgrades toward the stronger scheme.

| Choice | Aliases | Authorization |
| --- | --- | --- |
| `sr25519` | `sr` | Existing Sr25519 account; default |
| `ed25519` | `ed` | Existing Ed25519 account |
| `hashed` | | Permanent account with rotating Sr25519 keys |
| `mldsa` | `ms`, `ml-dsa` | Permanent account with rotating ML-DSA-65 keys |

New ML-DSA wallets default to 24-word mnemonics (256 bits of entropy). Other
schemes retain their 12-word default. Keep the ML-DSA default for new wallets;
a shorter phrase reduces the entropy protecting the master seed.

Record the selected scheme with the mnemonic. The same mnemonic under another
scheme derives a different account. Existing hashed wallet recovery and
transaction bytes remain unchanged. Selecting `mldsa` does not upgrade an
existing Sr25519 account in place; use the existing coldkey migration flow to
move to a newly created account.

Hashed and ML-DSA accounts require runtime support and registration. Register
and wait for finalization before publicly sharing their receiving address.
Their receiving addresses carry the network and public registration descriptor,
without revealing a spending public key. Funding and migration commands retain
that descriptor and use the existing registration flow. EVM access uses the
registered account's native authorization and permanent alias.

For fee-free PoW admission, a sponsor must first register both hashed or
ML-DSA keys and wait for finalization. The coldkey can then have a zero balance:
`btcli subnets register --pow` submits the direct PoW call without a registration
batch. The storage registration reserve is paid by the sponsor; PoW does not
waive that separate setup cost. Ed25519 and Sr25519 keys need no such setup.

The SDK reads the current generation and nonce from chain before signing.
Inclusion advances the generation even when the dispatched call fails. Dropping
a transaction before inclusion advances neither generation nor nonce; retrying
uses the chain's unchanged state and does not require updating a wallet backup.

**Use `mldsa` for post-quantum wallet signatures.** Its security does not depend
on keeping a public key secret after submission. A dropped Sr25519 transaction
still exposes its public key: hashing and rotation do not make classical
signatures quantum-resistant. This addition does not change consensus keys or
claim post-quantum security for the entire chain.

## Message signatures

`btcli wallet sign --message "challenge"` uses the wallet's stored scheme.
`btcli wallet verify --message "challenge" --signature HEX --ss58 ADDRESS`
uses the scheme bound into a descriptor-bearing receiving address. For a bare
SS58 address, supply `--crypto-type` from trusted knowledge of the signer:
for example, `--crypto-type mldsa`. The verifier never guesses the scheme from
the signature or falls back to a classical scheme. An explicit scheme that
conflicts with a receiving address is rejected.

Hashed account message signatures contain the original descriptor, identity
public key, and a domain-separated signature. They cannot authorize a runtime
transaction. A classical hashed wallet must first include a transaction that
retires generation zero; the CLI checks finalized state before revealing that
retired key. SDK callers pass that finalized generation as `hashed_generation`
to `wallets.sign_message`, or select it with `key.at_generation(generation)`.
ML-DSA message signing works without a chain query, including before registration.

ML-DSA transaction proofs contain 5,301 bytes; message envelopes contain 5,303
bytes. HTTP integrations must allow the larger hex signature header (10,608
characters including `0x`). Existing Ed25519 and Sr25519 message signatures
remain 64 bytes. External verifiers must support the selected scheme and its
message envelope; an older verifier cannot verify a new signature format.
HTTP servers must pass `expected_crypto_type` to `http_auth.verify`, using
trusted configuration or a registry lookup for the claimed sender. The request's
crypto header is not a trusted source for that decision.

Production registration remains disabled until the authorization benchmarks are
measured on reference hardware and the runtime is activated. ML-DSA has its own
`authorize_mldsa` benchmark and weight entry; unmeasured weights fail closed.
