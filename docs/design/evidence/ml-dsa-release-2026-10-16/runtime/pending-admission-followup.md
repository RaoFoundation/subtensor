---
title: "Pending RPC retains an admission isolation gap"
description: "Confirmed residual availability issue, exact runtime API coupling, and a bounded repair design."
---

**MEDIUM: unknown runtime exports can still starve EVM pending-state queries.** The executor buckets individual runtime API exports rather than the full public RPC operation. `node/src/execution_admission.rs:189-198` maps `EthereumRuntimeRPCApi_call/create/pending_block` to EVM, but leaves `EthereumRuntimeRPCApi_initialize_pending_block`, `Core_initialize_block`, and `BlockBuilder_apply_extrinsic` in Other alongside unknown exports. `vendor/frontier/client/rpc/src/eth/pending.rs:120-153` calls those Other APIs to construct pending state. Consequently `eth_getBalance(..., "pending")`, pending storage/code queries, and pending call/estimate paths depend on the allegedly unrelated Other budget, even though ordinary/latest EVM calls remain available. The state-query routes are `eth/state.rs:54,93,178`; the call route is `eth/execute.rs:139`.

A second manifestation occurs without an attacker. Other permits an initial burst of 16 and refills eight tokens per second (`execution_admission.rs:23-24,219-243`). Pending construction consumes separate tokens for initialization, inherents, and each pool extrinsic. Its loops immediately abort on a capacity error. A sufficiently fast reconstruction with more than the available burst cannot finish until it waits for refill; repeating the whole RPC can continually discard completed work and fail again. This is not an absolute count-only theorem: long execution naturally permits refill. The recorded 36-entry live pool demonstrates the realistic failure. The corrected fail-closed response prevents false partial balances, but does not make this operation available.

The existing public simulation retry helper does not repair pending construction. It recognizes one exact `runtime error: Execution failed: Other: ...` JSON-RPC error, while pending failures are wrapped as `Create pending runtime api error: ...`. Pending balance/storage/code have no outer retry loop at all. Merely moving known exports into the EVM bucket would couple pending reconstruction to unrelated EVM simulation and would still charge a burst token per extrinsic.

A bounded repair should reserve admission for the entire pending workload, while retaining per-execution protections:

1. Attach a private local pending-simulation marker/budget extension to the `ApiRef` constructed by Frontier. `ApiExt::register_extension` and executor `ExternalitiesExt::extension` already provide this mechanism; no new runtime export or on-chain protocol is required. An arbitrary `state_call` cannot create the internal marker. Route only the explicitly enumerated initialization/apply APIs bearing that marker to independent Pending capacity. Raw unknown exports and direct raw calls keep their normal budget.
2. Bound concurrent pending jobs and aggregate queued bytes. Keep per-call byte/concurrency admission and charge every actual execution, including retries. Preserve the global CPU/memory ceiling when adding a service; do not silently expand aggregate concurrency or input capacity.
3. Use one absolute deadline shared by initialization, all inherents, all pool transactions, and any final simulation. On a recognized capacity error, roll back only that attempt, await refill, and retry the **same** extrinsic while retaining the previously completed overlay. Do not restart the whole reconstruction, bypass admission, mislabel it Onchain, or retry ordinary runtime/validity errors. Apply retry backoff outside synchronous Wasm execution; cancellation must drop the waiting job without releasing any executing call's permit early.
4. Bound total attempted input/work and snapshot the pool once; do not permit endless scanning or repeated invalid entries. Return an explicit overload/deadline error when those limits are reached. Preserve included user dispatch-failure fees/nonces and invalid-pool-transaction skipping, and abort on failed inherents.

Required regression evidence: an exhausted Other bucket does not block a separately admitted empty pending job; raw RPC cannot forge the private marker; 32–36 inexpensive ready transactions complete after bounded refill with exact balance/nonce/state parity; genuine admission errors never produce partial success; the shared deadline/cancellation stops retries; caps remain enforced under simultaneous pending jobs; invalid transactions and failed inherents retain their exact commit/rollback semantics. This is proposed design only; no additional production changes were made.

Recorded pool test: `./live-pending-results.json`; offline independent review: `./live-pending-independent-review.json`. It shows 32 unique submitted transfer hashes, 36 observed pool entries, an explicit capacity response, and exactly 32 TAO at the finalized destination. It proves fail-closed behavior and aggregate finalized receipt. It does not preserve separate inclusion receipts for all 32 hashes and does not demonstrate successful pending reconstruction.

The isolated unknown-export reproduction passed on validator 20245, recorded in `./live-pending-isolation-results.json`. The first attempt waited for an empty pool and aborted before sending a flood; its log and script are preserved under `live-pending-isolation-empty-pool-attempt.*`. The completed test instead required fewer than eight pool entries and successful latest/pending balance baselines, then sent only 64 unknown-export reads. The pending query failed with the capacity error, the latest query succeeded, and pending recovered after refill. A direct malformed call to the named `EthereumRuntimeRPCApi_initialize_pending_block` export was itself rejected for capacity, proving that export shares the exhausted budget. The real pending RPC wrapper does not name the exact nested export that failed: initial initialization, fallback `Core_initialize_block`, and inherent/pool apply cannot be distinguished from that generic response alone. No signed transactions or chain state writes were submitted.
