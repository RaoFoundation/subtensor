## Confirmed defects corrected locally

1. **Protected EVM aliases were not reserved against contract creation.** `runtime/src/evm_origin.rs` reserved the owner's native nonce, but Frontier's EVM nonce comes from the separate legacy backing account (`vendor/frontier/frame/evm/src/lib.rs:1124-1128`). Registration left that EVM nonce zero. The EVM engine's CREATE/CREATE2 collision rule checks code and the EVM nonce, so an alias was eligible to become a contract before its first native EVM transaction. A targeted address collision would then install code with access to the protected balance and unrestricted native dispatch identity. Finding a matching 160-bit address is not a practical classical attack; nevertheless it is an unnecessary weaker hash-preimage condition in the PQ authority boundary and contradicts the explicit EOA reservation invariant. The correction initializes the independent EVM nonce to 1 after the freshness checks and retains its sufficient reference (`runtime/src/evm_origin.rs:114-123`). Previously used aliases continue to be rejected rather than having their nonce reset. The new runtime regression constructs a synthetic CREATE2 collision, proves creation succeeds before alias registration, then requires CreateCollision with no installed code after registration (`runtime/src/hashed_native_evm_tests.rs:515`). Existing reaping/pause coverage now also exercises both MS profiles and initial EVM nonce 1.

2. **Pending RPC silently accepted incomplete execution.** `vendor/frontier/client/rpc/src/eth/pending.rs` discarded all `apply_extrinsic` results while rebuilding pending state. The node limits offchain runtime calls in `node/src/execution_admission.rs`, so exhausted admission could omit genuine inherents or ready transactions while returning successful pending balance/storage/code queries. The correction propagates API errors, fails on invalid or failed inherents, rolls back and skips only invalid pool transactions, and retains included user-call failure fee/nonce effects. Three tests cover these exact outcome classifications. This uses honest overload propagation, without adding an independent nested retry budget.

3. **Malformed faucet work panicked instead of returning a dispatch error.** Metadata-driven signed-call coverage found `pallets/subtensor/src/subnets/registration.rs:426` converting an unconstrained `Vec<u8>` to H256. An empty vector (or any length other than 32) panicked in `H256::from_slice`. The faucet dispatch is gated by `pow-faucet`; feature-off production does not expose it, but all-features builds and localnets do. The correction rejects malformed lengths with the existing `InvalidSeal` before conversion. A focused Executive regression passed 20 cases (five malformed lengths for SR, ED, fixed MS, and rotating MS), including nonce/generation and no-mint event checks.

## Preexisting upstream weight-budget limitation

The pinned contracts pallet's `Contracts.migrate(weight_limit = Weight::from_parts(1, 1))` debug-panics when there is no active migration. `substrate/frame/contracts/src/lib.rs:1105` constructs a meter with `WeightInfo::migrate() + weight_limit`; `migration.rs:399` then unconditionally consumes `migration_noop()` after already consuming the base. The resulting `WeightMeter::consume` debug assertion fails. Release/WASM builds without debug assertions saturate rather than panic. This affects ordinary SR/ED equally and predates this feature. Under the user's explicit exclusion of weight work, the all-call matrix uses an explicit `migration_noop()` budget for that one call. No production filter or weight gate was changed. The debug repro is preserved in `./runtime-matrix-panic.log.gz`.

## Activation semantics requiring explicit release communication

The spec's master switch is a registration/authentication and capability-use pause, not a global freeze of all effects on an account. `AuthenticatedLimitOrderSignerFilter` currently checks only recovery/dispute, so AccountApproved orders previously committed by a protected account can still execute while the master/MS authentication switch is off. Preapproved mixed multisigs and announced proxy routes can similarly finish using cached authority and an ordinary final relayer. This is neither a fresh ML-DSA proof bypass nor demonstrated theft, but it must not be described as a total emergency spending freeze. An emergency policy intending to stop all cached authority requires coordinated order/proxy/multisig dispatch gating and cancellation/revocation recovery semantics. The runtime currently preserves permanent protection during a pause.

## Remaining limits

No static review or finite test suite establishes that users can never lose funds. Mathematical/implementation assurance still depends on the independently reviewed cryptographic primitive, key storage and recovery, operational key handling, clients and deployment configuration. This reviewer did not produce reference weights, benchmark or migrate production state, change spec_version, or alter activation policy. The corrected alias reservation adds a storage nonce write that must be included in the excluded reference-weight work. Existing used aliases remain fail-closed; if these experimental accounts were ever deployed, old aliases with zero independent EVM nonce would need a migration rather than assuming fresh-only registration.

Pre-registration disclosure is also an explicit protocol boundary (spec sections 76/80): hostile existing hotkey ownership or used EVM alias state can make registration fail closed. Direct descriptor registration and funding in one atomic transaction prevent partial funding when such setup fails. A bare AccountId receipt bypasses this SDK guard, so later recovery cannot be universally guaranteed if registration is blocked by hostile prior state. Register/finalize before publishing a new MS/hashed identity; this is not equivalent to an ordinary raw SR/ED public address.

## Additional confirmed pre-registration denial of service (not corrected)

`SubtensorModule.try_associate_hotkey` at `pallets/subtensor/src/macros/dispatches.rs:1701-1704` requires only the caller's signature and an arbitrary target hotkey AccountId. It forwards through `staking/account.rs` to `staking/helpers.rs:132,139-141`, which writes `Owner[target]=caller`, `OwnedHotkeys` and `StakingHotkeys` for an unassociated target. For an unregistered descriptor-derived target the runtime considers its authority Unrestricted, so any ordinary attacker can establish this association without knowing the target's private key, paying a burn, or registering a subnet. `runtime/src/hashed_auth.rs:315-321` then refuses ML-DSA descriptor registration because the existing owner is not PQ-protected. The same direct-address receipt cannot be spent until registration succeeds. Global hotkey swap by the existing owner with `keep_stake=false` removes the old Owner entry (`swap_hotkey.rs:631`), but the victim has no unilateral owner-removal route. Thus an attacker can front-run descriptor disclosure and block setup; already bare-funded TAO can be trapped absent attacker cooperation or privileged remediation. Atomic descriptor registration/funding prevents a sender adding funds after this failure, but does not remove the setup denial of service. Restoring owner control safely needs an authenticated initial-key migration/recovery path or a complete quarantine policy for legacy weak-owner privileges; merely deleting ownership in sponsor registration or permitting a weaker owner violates separate security invariants. This deserves a release-blocking decision beyond a documentation caveat.

The executable `disclosed_unregistered_ms_address_can_be_blocked_by_hostile_hotkey_association` regression passed for both MS profiles: an attacker established Owner without the victim key, ordinary native funding succeeded, registration failed with `MlDsaHotkeyRequiresPqOwner`, and the genuine initial MS signature could not spend the balance. The same static mechanism affects classical hashed SR/ED through `HashedHotkeyRequiresHashedOwner` at `runtime/src/hashed_auth.rs:604-608`.

## Follow-up availability finding

Independent pipeline review confirms that unknown-export admission can still starve EVM pending reconstruction because initialization and per-extrinsic BlockBuilder calls remain in Other. The 36-entry live pool test demonstrates correct fail-closed errors and 32 TAO finalized receipt, but it also demonstrates that a legitimate sufficiently fast pending reconstruction can exceed the 16-token burst. This is a residual MEDIUM availability issue; it is not fixed by the pending error-propagation correction. The bounded workload-marker/shared-deadline repair proposal and required regressions are in `./pending-admission-followup.md`. No additional production changes were made.

An isolated live reproduction on validator 20245 confirmed this independently of the large pool: four ready entries before and after, successful pending baseline, 64 unknown runtime-export reads over 23 ms, 48 capacity rejections, then failed pending balance while latest balance remained available. A direct probe of `EthereumRuntimeRPCApi_initialize_pending_block` also failed for admission capacity; the actual pending RPC wrapper did not identify its nested failure stage. Pending balance succeeded again after refill. The probe sent no signed transactions or state writes. Exact RPC responses, runtime hash and limitations are recorded in `./live-pending-isolation-results.json`.

The independent mainnet rehearsal post-verification is `./mainnet/post-verification.json`; its acquisition-log evidence limitations are explained in `./mainnet/post-verification.md`. All ten contiguous synthetic empty blocks and all recorded artifact hashes passed, but this does not remove either the pre-registration funds-safety blocker or the pending availability gap.

The acquisition-log limitation was subsequently closed with a separate logged download of the same pinned block. It proves 3,304,807 unique top-level keys, 56 child tries and 926,483,590 serialized bytes, with the exact RPC-pinned root. The snapshot bytes differ from the original serialization, so the unchanged strict runner was repeated against the new snapshot. The unchanged full checker then passed, including exactly ten synthetic empty blocks, per-block root/signature checks and full-state decode, source/candidate version checks, and migration idempotency. Complete result: `./mainnet/logged-full-verification.json`; provenance: `./mainnet/logged-acquisition-manifest.json`. The original narrower verification is retained as historical evidence. The durable mainnet README explains the excluded weight warnings, disabled multiblock-migration checks for `MultiBlockMigrator = ()`, and why synthetic empty blocks are not canonical mainnet transaction-body replay.
