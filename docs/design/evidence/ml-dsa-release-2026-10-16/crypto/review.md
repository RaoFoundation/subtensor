## Confirmed finding and local repair

**Wallet backup corruption on a short OS write.** Baseline `sdk/python/bittensor/keyfiles.py:151` called `os.write` once, ignored the byte count, fsynced, and replaced the previous file. Fault injection produced success while replacing a complete previous backup with only 15 of 30 intended bytes. The baseline also reused a predictable `.tmp` pathname, permitting concurrent writers to interfere and following a pre-existing temporary symlink.

Current `sdk/python/bittensor/keyfiles.py:130-178` uses an exclusively created unique temporary file, retains mode 0600, loops until every byte is written, rejects zero progress, syncs the full file before publication, and syncs the parent directory on POSIX. Failures before publication preserve the original file. A parent-directory sync failure occurs after publication: it propagates an error while leaving the complete new wallet recoverable, but cannot promise that the old file remains or that the rename is durable across a subsequent crash. Overwrite refusal is atomic, including two concurrent first-time writers, by publishing with a no-clobber link. Explicit/interactive overwrite uses atomic replace. Temporary files are removed on success or failure. This does not change wallet encoding, encryption, keys, or address derivation. A filesystem that cannot perform the required atomic publication fails rather than silently weakening it.

Reproduction: `keyfile-short-write-repro.py`, baseline output `keyfile-short-write-results.log.gz` in this directory. Regression: `sdk/python/tests/unit/test_keyfile_atomicity.py` covers short/zero writes, partial write followed by error, file sync failure, replace failure, cleanup, concurrent overwrites, concurrent no-clobber publication, pre-existing shared-temp symlink, ordered durability sync, a directory-only sync failure with complete ML-DSA wallet recovery, and declined overwrite.

Validation: **18 passed, 1 skipped** across atomicity and existing keyfile golden tests (`keyfile-tests.log.gz`). The skipped legacy Fernet fixture requires an unavailable Python `cryptography` package; this is not an ML-DSA fixture. Ruff check/format, ty, and diff-check passed for the changed files.

- `sdk/bittensor-core/src/keys/mldsa.rs:29-106,156-208,255-319,324-438`: HKDF-SHA512 binds version/profile/role/generation; transaction, order, and message keys are separate; OS CSPRNG supplies hedged signing randomness; fixed mode retains its transaction key but advances replay generation; authorization verifier binds trusted descriptor/current commitment/generation; capability proofs bind owner/genesis/role/epoch and independently resolved registry commitment; order signatures bind canonical runtime order bytes.
- `sdk/bittensor-core/src/keys/mod.rs:310-361`: ML-DSA requires 24-word BIP39, uses the first 32 bytes of the standard BIP39 seed, handles derivation passphrase separately from encryption password, and does not persist a phrase that cannot recover the password-derived seed alone.

- `sdk/bittensor-core/src/keys/receiving.rs:97-141`: exact 104-character bth2 encoding, canonical base64, checksum, descriptor support. Receiving format is network independent; authorization remains chain bound.
- `sdk/python/bittensor/mldsa_signing.py:47-92,147-222`: imported signing requests are reconstructed using trusted runtime metadata and expected genesis, wallet descriptor/current commitment are checked, and attached proofs verified before assembly.
- `sdk/python/bittensor/mldsa.py:62-100`: message capabilities resolve one finalized snapshot, enforce activation/role/audience/epoch/expiry; proof-supplied authority is not trusted as a grant.
- `runtime/src/hashed_extrinsic.rs:78-145,231-302,345-357` and `runtime/src/hashed_auth.rs:186-269`: unchanged signed-v4 carrier, bounded raw address decoding, fixed Ed25519 marker cannot authorize by itself, state/resource checks precede expensive verification, normal nonce/fee/origin extensions still apply. Authorization consumes generation outside inner-call rollback; outer invalidity rolls state back.
- `pallets/hashed-accounts/src/mldsa.rs:409-486`: current generation/profile/key commitment and next-commitment policy checked both at authorization and consumption; checked generation increment; failed inner calls cannot reuse the old generation. No further concrete cryptographic authorization flaw was established in these paths. This is a bounded manual review and test result, not a universal absence-of-bugs claim.

## Cross-review of concurrent fixes

**Shield explicit nonce:** current `_transport/interface.py:770` correctly preserves a supplied nonce. Real private signing still checks it equals confirmed nonce plus the permitted generation offset before assembly. Dummy quotes can therefore use the actual inner nonce+1, including SCALE compact boundaries, without private signing; generation itself is fixed-width. External proofs retain their signed nonce while runtime validity still checks signature, nonce, and generation. No origin/authority weakening found.

**EVM alias reservation:** current `runtime/src/evm_origin.rs:118-123` reserves the independent backing EVM nonce as 1 after strict freshness validation and donation sweep, before installing the alias. A sufficient reference keeps this nonce alive. All registration callers execute transactionally, so failed registration rolls it back. CREATE/CREATE2 then sees a nonzero nonce before any user EVM operation, preventing contract code from acquiring that alias's native identity after a destination collision. Owner-origin checks and Ethereum-authority rejection remain unchanged. First EVM transaction/CREATE uses nonce 1, which SDK nonce queries should obtain; tests cover this behavior.
