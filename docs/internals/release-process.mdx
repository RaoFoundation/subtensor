---
title: Release process
description: How a merge to main becomes a runtime upgrade on devnet, testnet, and mainnet, and how the release train's artifacts are published.
---

Shipping is a single pipeline: **`release-train.yml`** runs on every push to
`main`, builds the runtime once, and promotes that identical wasm through the
networks. A second workflow, **`watch-mainnet-release.yml`**, watches the
chain and publishes release artifacts once the mainnet upgrade actually
executes.

## The release train

```
push to main
  └─ srtool build (once per train)
       ├─ deploy devnet ───── smoke-check devnet
       │    └─ deploy testnet ── smoke-check testnet ── publish SDK rc to PyPI
       └─ plan stable Python ── build stable wheels + SDK (no credentials)

one `mainnet` approval starts three jobs together:
  ├─ propose mainnet upgrade (multisig)
  ├─ wait for mainnet to run this wasm ── publish stable Python to PyPI
  └─ wait for mainnet to run this wasm ── deploy production docs
```

### Build once (srtool)

The train builds the runtime with [srtool](https://github.com/paritytech/srtool)
— a pinned Docker build environment that makes the wasm **byte-reproducible**.
The artifact (`subtensor.wasm` + digest) is uploaded once and reused by every
deploy job; promotion never rebuilds. Anyone can verify the hash independently
by running `scripts/srtool/build-srtool-image.sh` followed by
`scripts/srtool/run-srtool.sh` locally (see
[Repository scripts](/docs/internals/scripts)).

### The ship lever: `spec_version`

Every deploy job first compares the built runtime's [`spec_version`](/code/runtime/src/lib.rs#L238)
(`runtime/src/lib.rs`) with what the target chain is running, and **no-ops
unless the build is newer**. Consequences:

- A merge without a `spec_version` bump builds and then does nothing — this
  is deliberate, and it's why the Spec Version Check on PRs exists (label
  `no-spec-version-bump` to opt out knowingly).
- Stale queued trains are harmless: they no-op at each guard.
- Rollback is not a concept here — you ship a *newer* fixed version.

### Promotion gates

Human approval lives in GitHub **environment settings**, not workflow code:

| Stage | Environment | Gate |
|-------|-------------|------|
| devnet | `devnet` | none — deploys automatically, then runs the devnet smoke suite |
| testnet | `testnet` | environment reviewers (one-click approval), then smoke suite; the SDK release candidate to PyPI asks for its own `testnet` approval |
| mainnet | `mainnet` | environment reviewers **plus** the multisig ceremony below; the one approval also starts the stable PyPI and production docs jobs, which publish once the upgrade executes |
| release | `mainnet-release` | none — the executed multisig is the approval; see [the release watcher](#the-release-watcher) |

Deploys to devnet and testnet are direct `setCode` transactions via the CI
deploy key. After the on-chain `spec_version` is verified, the train moves the
corresponding network mirror branch. That branch push triggers both Docker
publishers from the exact deployed commit, updating the matching `:devnet` or
`:testnet` tag in `ghcr.io/raofoundation/subtensor` and
`ghcr.io/raofoundation/subtensor-localnet`. It does not move either package's
`:latest` tag. The smoke suite then validates the live network while the
independent image builds run.

### The mainnet multisig ceremony

CI never upgrades mainnet directly. Before any on-chain action, the train
reserves the immutable `v<spec_version>` tag at the exact source commit. Its
final job then submits a **multisig proposal**: the CI key is one half of a
2-of-2 deployment multisig that holds a `SudoUncheckedSetCode` proxy on the
sudo key. The triumvirate then approves the proposal 2-of-3 **out-of-band** —
no GitHub credential can unilaterally change the mainnet runtime. Until they
sign, nothing happens on chain.

For rehearsal, the `mainnet-clone` PR label spins up a live clone of mainnet
running your runtime with a public endpoint
([mainnet clone testing](/docs/internals/mainnet-clone)).

## The release watcher

`watch-mainnet-release.yml` polls mainnet every 10 minutes. When an upgrade
executes, it resolves the release-train artifact whose commit matches the
immutable tag and whose runtime hash matches the finalized on-chain `:code`.
The triumvirate's signatures already approved that exact runtime, so the
watcher publishes the release without waiting for anyone:

1. **`mainnet` mirror** moved to the release commit. The push publishes the
   production Docker images `:mainnet`, `:v<spec_version>`, and `:latest`
   and the localnet images `:mainnet` and `:v<spec_version>`.
2. **GitHub release** `v<spec_version>`: the release train's proposal
   pre-release becomes the final, latest release with the verified runtime
   assets attached.

This job runs in the `mainnet-release` environment, which admits only `main`,
has no reviewers, and holds only the mirror deploy key. It rechecks the
finalized runtime before touching the mirror and never rewrites a final
release.

### Stable Python and docs: one approval

Stable PyPI packages and the production docs need credentials that live in
the `mainnet` environment. GitHub asks for a new approval for every job that
reaches a protected environment after the click, so the release train
creates those jobs next to `propose-mainnet` with the same `needs`. They
reach the environment together and the one "deploy to mainnet" approval
starts all three:

3. **Python SDK + bittensor-core wheels** to PyPI (trusted publishing, with
   PEP 740 provenance attestations)
4. **Production website/docs** to Vercel

Each job waits inside the approved job, polling finalized mainnet every two
minutes, until the runtime is this train's exact wasm (spec and `:code` hash)
and the immutable `v<spec_version>` tag names this train's commit. Then it
publishes. The wheels and SDK are built earlier in the train, beside the
devnet/testnet stages, in jobs with no environment and no id-token, and that
build is not a dependency of the proposal: a Python failure never blocks or
re-runs `propose-mainnet`.

| What happens | Result |
|---|---|
| Upgrade executes | publish, usually within two minutes of finality |
| Mainnet moves past this spec, or `main` carries a newer spec | stop without publishing (a newer train is queued); a warning on the run says how to publish if this spec still goes live |
| `propose-mainnet` fails | the waiting jobs fail too |
| Mainnet runs a different wasm under this spec | fail, nothing is published |
| Not executed within 20 hours | fail; publish later as below |
| Stable build failed | the PyPI job fails; fix, then re-run failed jobs (one approval) |

**Publishing after a late upgrade.** A staggered testnet → mainnet rollout
never makes publishing impossible. Once the runtime is live on mainnet, either:

- dispatch `watch-mainnet-release.yml` from `main`. It rebuilds the wheels
  from the `v<spec_version>` tag and publishes whatever PyPI is missing. It
  has no deadline: it works for as long as that runtime is the one on
  mainnet. Redeploy the docs with `deploy-docs.yml` (production). Or
- re-run the train's failed jobs. This works within GitHub's 30-day re-run
  window (the stable dist artifact is kept as long) and when no newer train
  is running, because the re-run joins the `release-train` queue. The PyPI
  and docs jobs start together, so one click covers both.

Each path asks for one `mainnet` approval. Packages are only ever published
for the runtime mainnet is running: once a newer runtime goes live, the
older runtime's stable versions are skipped, and the newer runtime ships its
own.

While these jobs wait (up to 20 hours; the job's `GITHUB_TOKEN` cannot
outlive 24), the run holds the `release-train` concurrency group, so a newer
train queues behind it. That is why waiting stops as soon as `main` carries a
newer `spec_version`.

This ordering means the release always reflects what is *actually running on
mainnet*, not what was merged.

PyPI is the terminal state for stable Python publication. Completeness
requires the SDK wheel and source distribution plus the full `bittensor-core`
Linux and macOS wheel matrix and source distribution. Every file must carry a
PEP 740 attestation from this repository's release train, release watcher, or
stable Python workflow on the `mainnet` environment. Scheduled watcher runs
never request a PyPI or docs approval. Dispatch the watcher to retry a
failed, partial, or missed upload (for example a train that gave up waiting,
or a runtime deployed outside the train), even if the GitHub release already
exists or the release-train artifact has expired. That retry asks for its
own `mainnet` approval. Retries require the release target, immutable tag,
protected `mainnet` mirror, and finalized runtime bytes to agree. The SDK's
committed `X.Y.Z.dev0` version is stamped to `X.Y.Z` for this build. The
release train rejects a base SDK or core version that already exists on PyPI
before publishing release candidates, and warns when a runtime would ship no
new stable packages for the same reason. Releases through v432 predate
automated stable Python publication and are handled as historical state. A
missed website deployment can be redeployed with `deploy-docs.yml`
(production).

### Docker images

Every mirror branch publishes its own moving tag from the exact commit it
points at: `:devnet`, `:testnet`, and `:mainnet`. Only the `mainnet` build
also publishes the immutable `:v<spec_version>` tag, after checking that the
commit is still the mirror head and carries that release tag. Production
`:latest` moves only with it, so `:latest` is always the node running on
mainnet. Every merge to `main` publishes the moving `:main` tag, so
developers can prepare against merged features before they reach mainnet.
Localnet `:latest` remains an alias for its `:main` image. To republish the
current mainnet images, dispatch `docker.yml` with `tag=mainnet` and
`docker-localnet.yml` with `branch-or-tag=mainnet`.

## Hotfixes

The same pipeline applies: land the fix on `main` with a `spec_version` bump
and let the train promote it. There is no side channel that skips devnet and
testnet validation.
